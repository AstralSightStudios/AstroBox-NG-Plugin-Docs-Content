> 事先提醒这个东西建议丢给 Agent 当 Prompt，当然最好是智商在线的（推荐 gpt-6.1 Sol / claude 同级别模型，DS V4.1F 也凑合）

## 包和 ELF 各有多大

`.canopus` 的总大小是压缩过的，先给包跑一次 `tar -tvf`，看清楚到底是哪些文件在占地方。这里有个常见误判：多固件包可能带好几份 ELF，包变大不代表单台设备要加载的那份也变大。比较时要用同一个固件 target、同一套 SDK 和发布配置，改动前后分别记下包和 ELF 的大小才是最重要的。

ELF 用 `llvm-size -A` 看各节。涨在 `.text`，通常去查代码和依赖；涨在 `.rodata`，优先怀疑 `include_bytes!` 带进来的位图、字形和查找表。`.bss` 在文件里几乎不占空间，加载时却要实打实分配，别因为文件没变大就忽略它。另外，校验报告里的 `resident_bytes` 只统计加载节的大小，打开页面后才分配的位图和缓冲不在里面，这部分要另外测。

## 缩小模块和资源

Canopus 默认已经按体积优化过编译：Rust 用 `opt-level=z` 和 Thin LTO，C 用 `-Os`。所以先别急着改编译参数，去看看发布构建实际启用了哪些 Cargo feature。演示页可以单独放在一个 feature 下，但只关掉页面入口往往不够，资源表里还引用着的图片照样会进 ELF。包里单独存放的文件，则去查 [`Canopus.toml` 的资源列表](/docs/canopus-dev/module-project#打包资源文件)。设备真正用的是导出后的位图，源图和预览图可以留在工程里，不必跟着发布。调整过链接选项的 ELF 要重新[打包校验](/docs/canopus-dev/release#构建与校验)，加载器还需要重定位信息，这一步不能省。[CLI 构建参数](https://github.com/AstralSightStudios/Canopus/blob/main/cli/canopus/src/project.rs)

位图按实际显示尺寸导出，空白的透明边该裁就裁。卡片换宽度时，四角可以复用，只拉伸或平铺直边；只差颜色的状态也能共用一张图，在绘制时着色，没必要每种状态都塞一张。整层都不透明、后端又支持的话，用 RGB565 比带 Alpha 的格式省不少。数字动画可以只打包数字和分隔符，普通字体按发布语言裁剪；如果文案是动态的，还要检查回退字体有没有被一起裁掉。

有些固件只读未压缩位图，那就把压缩文件带进包，第一次用到时分块解码到数据目录。一块缓冲反复用即可，不必把整张解码后的图长期留在内存里，但磁盘上还是要给原尺寸位图留足空间。已有文件用版本或哈希判断是否重用，只看大小会漏掉长度相同但内容变了的更新。写入时先落临时文件，解码完整再替换，避免下次打开读到半张图。

## 动画播放时掉帧

只动前景的时候，底板就让它留在原处，别让缩放或位移牵着整个容器重新排版。数字槽位建一次，哪位数字变了就更新哪位；滚动动画里图片源没变，也不用每一帧重复设置。进度条的像素位置没变时，可以跳过这次更新；滚出屏幕的卡片先别画，等滚回来再补。

几组数字同时滚动还是卡，就优先保当前操作的那一组动画，其余直接显示新值。用户更在意自己正在调的那一项，别为了“全都动起来”把帧预算耗光。帧回调要在动画结束或页面离开时停掉，业务更新照常走，不要把两者绑在一起。动画进度按已经过去的时间算，卡掉的那几帧不用补画，否则恢复时反而会突然快进。

## 弹窗打开慢

如果能接受弹窗背后的页面静止，可以在弹出前抓一次背景，把快照缩小后做横向和纵向滤波，再压暗、放大，作为弹窗底图。弹窗进出都沿用这张图，背景真的变了才重新抓。输出不需要透明度时，同样可以用 RGB565。

这里有个容易算漏的地方：滤波用的小图，不等于快照本身也变小了。算峰值内存时，原尺寸快照、滤波工作区和输出图都得算进去。减少透明图层覆盖的面积，素材本身已经有圆角，就别在外层再剪一遍。抓不到快照，或者用了快照打开仍会停顿，退回半透明遮罩也比硬做好。页面离开后，记得释放留作复用的缓冲。

## 真机上怎么测

在同一台设备上，把首次打开和再次打开分开测，别把首次解包的耗时算进每次进页的成本。打开慢就分段记：解包、创建控件、抓快照各花多久。播放中有停顿，翻帧间隔记录，平均帧率看不出是哪几帧被拖长了。退出页面后再看一眼动画占用的内存有没有释放。

裁剪和过渡效果可以先在 [Mirage](/docs/canopus-dev/mirage) 里看个大概，帧耗时和峰值内存还是要以真机为准。页面退出时该停哪些回调，见 [App 生命周期](/docs/canopus-dev/app-lifecycle)。
